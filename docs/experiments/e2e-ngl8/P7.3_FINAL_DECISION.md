## 1. Root Cause: T2W Drain Race Condition

### The Bug

`stream_decode()` in omni-cli returns when the LLM generates EOS. But the TTS worker runs asynchronously — it may not have started generating audio tokens yet. The old code in `omni_stop_threads()` drained T2W before TTS had output any tokens, resulting in 0 WAVs and silently successful exit (rc=0). The caller received rc=0 but no audio.

### The Fix (91e5674)

Two-phase stop protocol:

```
Phase 1 (omni_stop_threads):
  LLM.stop() → TTS.stop() → T2W KEPT ALIVE

Phase 2 (omni_free / omni_prepare_for_reuse):
  TTS.join()          ← TTS is done, T2W buffer is populated
  T2W.drain(signal EOS, wait for is_final_processed)
  T2W.stop()
  T2W.join()
```

The drain uses `std::condition_variable::wait_for()` with `OMNI_T2W_DRAIN_TIMEOUT_MS` (default 5000ms). If the drain times out, the terminal output is classified as `DRAIN_TIMEOUT`, and exit code reflects the failure.

### State Machine

```
IDLE → RUNNING → EOS_SIGNALED → COMPLETE (is_final processed)
                              → FAILED (timeout or error)
```

Per-request tracking in `T2WThreadInfo`: `drain_state`, `eos_received`, `is_final_processed`, `wav_count`, `terminal_output`, `feed_window_errors`.

## 6. Production Recommendation

### RECOMMEND_OPT_IN: `OMNI_KV_CACHE_REUSE=1`

KV cache reuse is production-ready as an **opt-in feature**. It delivers:

1. **59.0% request_to_first_audio reduction** (9642ms p50 improvement, the user-perceived latency from request to first sound)
2. **2772x prefill speedup** (eliminates redundant audio+vision encoding)
3. **96.9% valid rate** with no T2W drain failures

**Scope:** PASS_FOR_TESTED_STATIC_PREFIX_WORKLOAD. GENERAL_PRODUCTION_READINESS: NOT_YET_APPROVED
(8 boundary conditions untested).

### Why DEFAULT_OFF

KV cache reuse remains DEFAULT_OFF because:

1. The T2W drain fix (91e5674) is still recent — a more extensive production soak would be prudent before changing defaults
2. Long responses can hit the 120s timeout on the B arm (2/32 = 6.3% of B runs), though this is comparable to the 120s ceiling on A-arm very long responses
3. The feature stores cache files in `/tmp/` (not configurable) — production deployments may want a configurable path
4. Only tested with static prefix workload (same model, tokenizer, RoPE, chat template) — no evidence for cross-configuration cache behavior

### Enabling in Production

```bash
OMNI_KV_CACHE_REUSE=1 llama-omni-cli -m model.gguf --omni ...
```

The first request populates the cache (`/tmp/omni_kvcache_<hash>.bin`, ~9 MB). Subsequent requests reuse it, eliminating ~10 seconds of prefill latency.
